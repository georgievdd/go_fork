# Домашнее задание №2: проверка заказов магазина

Продолжаем магазин из [первого задания](../01/README.md). Поставщик сообщает, что
в некоторых поставках могут быть проблемные товары. Нужно найти заказы с этими
товарами, уточнить риск у поставщика и сохранить результат проверки.

Например, пришло уведомление о чае из поставки №17. Это ещё не значит, что весь
чай опасен: поставка №18 может быть в порядке. Более того, даже для поставки №17
нужно получить подтверждение от поставщика.

Ваша программа `order-report` будет выполнять эту работу и выводить журнал
событий. Основная тема задания — горутины и каналы: несколько этапов работают
одновременно, передают результаты друг другу и корректно завершаются.
HTTP-сервер и настоящую базу данных писать не нужно: вместо них даны готовые клиенты.

Быстрая навигация: [вход и результат](#вход-и-результат-программы),
[клиенты](#самое-важное-файлы-заказов-и-поставщика-читают-клиенты),
[каналы](#часть-1-работа-с-каналами), [проверка заказов](#часть-2-проверка-заказов),
[отчёт](#формат-отчёта), [данные](#входные-данные), [запуск](#запуск-программы),
[критерии проверки](#критерии-проверки), [тесты и сдача](#тесты-и-сдача).

## Вход и результат программы

На вход `order-report` получает четыре обязательных флага с путями к CSV
и список путей к файлам уведомлений через stdin:

| Источник | Что передать |
|---|---|
| `-products` | Путь к каталогу товаров, например `testdata/products.csv` |
| `-supplies` | Путь к составу поставок, например `testdata/supplies.csv` |
| `-orders` | Путь к CSV заказов, например `testdata/integration/orders.csv` |
| `-supplier-status` | Путь к CSV ответов поставщика, например `testdata/integration/supplier-status.csv` |
| stdin | Пути к CSV уведомлений, по одному на строку; готовый список — `testdata/suppliers-input.txt` |

`orders-input.txt` — вспомогательный файл с одним путём: его содержимое
передаётся в `-orders`. Содержимое `suppliers-input.txt` подаётся в stdin.
Полный пример команды приведён в разделе [«Запуск программы»](#запуск-программы).

Результат работы состоит из двух частей:

1. **Журнал событий в stdout** в формате
   `<state> <order_id> <true|false|unknown> <line_ids|->`.
   Например, успешная проверка и сохранение двух заказов могут дать:

   ```text
   pending 1001 true 1,4
   confirmed 1001 true 1,4
   pending 1002 false -
   confirmed 1002 false -
   ```

2. **Сохранение результатов проверки через `ordersClient.SetRisk(...)`**:
   признак риска и номера рискованных строк каждого успешно проверенного заказа,
   включая результат `false`. Пометки хранятся в памяти клиента в рамках текущего
   запуска. Исходные CSV не меняются; отдельный файл с рисками создавать не нужно.

Диагностика ошибок выводится в stderr; при успехе он пуст. Журнал из stdout
можно сохранить в файл перенаправлением `>`. Формат событий и поведение при ошибках
описаны в разделе [«Формат отчёта»](#формат-отчёта), коды завершения -
в разделе [«Запуск программы»](#запуск-программы).

## Самое важное: файлы заказов и поставщика читают клиенты

**Не открывайте и не разбирайте CSV заказов, статусов поставщика и уведомлений
в коде своего решения. Передавайте клиентам только пути к файлам: они сами
прочитают CSV, проверят формат и вернут готовые данные.**

Оба клиента создаются одинаково. Например, внутри функции, возвращающей ошибку:

```go
ordersClient, err := orderclient.New(ordersPath)
if err != nil {
    return err
}

supplierClient, err := supplier.New(statusPath)
if err != nil {
    return err
}
```

Здесь `ordersPath` — значение флага `-orders`, а `statusPath` — значение
`-supplier-status`. Собирать карты для конструкторов самостоятельно не нужно.

Дальше работайте через методы клиентов:

```go
orders := ordersClient.Orders() // map[model.OrderID]model.Order, уже готовые заказы

notices, err := supplierClient.ReadNotices(noticePath) // []supplier.Notice
if err != nil {
    return err
}
```

`Orders()` возвращает независимую копию заказов с их позициями. По ней можно
строить индексы и искать нужные заказы. `ReadNotices(path)` возвращает уведомления
с полями `ProductCode`, `SupplyID` и `Reason`. Повторы остаются в результате:
устранять повторную обработку должен ваш конвейер.

**Ответ о риске получайте только через `supplierClient.IsProblematic(...)`,
а сохраняйте результат только через `ordersClient.SetRisk(...)`.**
Уведомление — повод проверить товар, а не готовый ответ о его безопасности.
Не вычисляйте ответ поставщика по коду товара, причине уведомления или `expected.txt`.

CSV заказов и статусов лежат отдельно, в [testdata/integration/](testdata/integration/).
Они задают данные учебных клиентов. В своём коде вы указываете пути к ним,
а содержимое получаете через клиентов. Эти файлы нельзя изменять при обработке.

| Данные | Как с ними работать |
|---|---|
| `products.csv`, `supplies.csv` | Самостоятельно прочитать каталог и состав поставок |
| `integration/orders.csv` | Передать путь в `orderclient.New`, получить заказы через `Orders()` |
| `integration/supplier-status.csv` | Передать путь в `supplier.New`, проверять пары через `IsProblematic()` |
| `notices/*.csv` | Передавать каждый путь в `supplierClient.ReadNotices()` |

Конструкторы загружают данные один раз. Чтобы следующий запуск использовал
обновлённые файлы, создавайте новые клиенты. Для совместимости также оставлен
`supplier.Load(path)` — он делает то же самое, что `supplier.New(path)`.

## Часть 1. Работа с каналами

Реализуйте функции в [internal/pipeline/pipeline.go](internal/pipeline/pipeline.go):

```go
type Stage func(in <-chan any, out chan<- any)

func RunPipeline(stages ...Stage)
func Merge(inputs ...<-chan any) <-chan any
func Tee(input <-chan any) (left, right <-chan any)
```

Этот пакет ничего не знает о магазине, заказах или поставщиках.

### RunPipeline: соединить этапы

Каждый этап запускается в отдельной горутине. Его выход соединяется со входом
следующего этапа каналом с ограниченной ёмкостью. Следующий этап начинает
обрабатывать значения, пока предыдущий ещё работает.

Правила запуска и завершения:

- Первый этап получает закрытый пустой вход. Последний только читает и ничего
  не отправляет в свой выход.
- Этап не закрывает переданные ему `in` и `out`. Его выход закрывает `RunPipeline`
  после возврата функции этапа.
- Если этап запускает собственных работников, он ждёт всех их отправок до возврата.
- `RunPipeline` возвращается после завершения всех этапов, включая завершающие
  действия последнего.
- Без этапов функция сразу возвращается. Единственный этап получает закрытый
  вход и ничего не отправляет.

Внутри горутины вызывайте каждый этап через готовый трассировщик:

```go
stagetrace.Run(stage, in, out)
```

Он вызывает функцию с исходными каналами и записывает начало и конец её работы.
Запуск горутин, ожидание и закрытие каналов остаются вашей задачей.
`nil` вместо функции этапа, неверные типы сообщений и восстановление после
`panic` в контракт не входят.

### Merge: собрать несколько входов в один

Функция сразу возвращает новый канал и конкурентно читает все входы. Медленный
открытый канал не должен мешать передаче значений из готового канала.

Каждое значение нужно передать ровно один раз. Порядок внутри каждого входа
сохраняется, а между разными входами может быть любым. Выход закрывается, когда
все входы прочитаны и все значения переданы, в том числе из буферов закрытых каналов.

`nil`-входы пропускаются. Без входов результат — закрытый пустой канал.
Один и тот же ненулевой канал несколько раз передавать не нужно.

### Tee: передать каждое значение в две ветки

Функция возвращает два разных канала с ограниченной ёмкостью. Каждое входное
значение должно попасть ровно один раз в каждую ветку, с сохранением исходного порядка.

Готовая ветка получает текущее значение, даже если другая пока не может его
принять. **Следующее значение из входа можно читать только после отправки
текущего в обе ветки**, в том числе в их буферы.

После чтения всего входа и передачи оставшихся значений оба выхода закрываются.
Для `nil`-входа оба выхода сразу закрываются. Обе ветки нужно читать до конца.

Несколько работников на одном канале делят задачи между собой. `Tee` нужен,
чтобы одну задачу получили оба потребителя. Глубокого копирования здесь нет:
общие срезы, карты и объекты по указателям нужно только читать либо копировать
перед изменением.

## Часть 2. Проверка заказов

Используйте свои `RunPipeline`, `Merge` и `Tee`, чтобы связать поиск заказов,
проверку, сохранение и вывод отчёта. Интеграционные тесты запускают CLI, а не
вызывают ваши бизнес-функции по именам.

### Как определить риск

Сначала сопоставьте коды из уведомлений с товарами каталога и объедините пары
`(product_id, supply_id)` из всех уведомлений. Один товар может быть указан под
разными кодами: это всё равно один товар.

В обработку попадают **все заказы с выбранными товарами**, включая заказы,
где тот же товар пришёл из другой, безопасной поставки. Заказы без выбранных
товаров не попадают в отчёт. Сами заказы берите из `ordersClient.Orders()`.

Позиция заказа рискованна, если выполнены оба условия:

- её пара `(product_id, supply_id)` есть в уведомлениях;
- `IsProblematic(product_id, supply_id)` вернул `true` без ошибки.

Проверьте все подходящие позиции заказа. Результат — признак риска и список
рискованных `line_id` без повторов, по возрастанию. Заказ рискованный, если
список непустой. Один товар может занимать несколько разных строк заказа.

Каждый заказ обрабатывается один раз за запуск. Повторные пути, уведомления,
коды и пересечения выборок не должны приводить к повторным сохранениям.
Успешную проверку сохраняйте ровно один раз, **включая результат `false`**:
он снимает прежнюю пометку риска.

Ошибка проверки означает неизвестный риск. Такой заказ не сохраняется и
получает событие `error` с `unknown`. Ошибка одной пары не должна мешать
обработке заказов, в которых её нет.

### Что предоставляют клиенты

| Метод | Назначение | Задержка | Лимит одновременных вызовов |
|---|---|---:|---:|
| `IsProblematic(productID, supplyID uint64) (bool, error)` | Проверить пару товар–поставка | 3 мс | 8 |
| `SetRisk(id model.OrderID, risky bool, riskyLines []uint64) error` | Сохранить вычисленный результат | 4 мс | 8 |

Лимит относится к каждому клиенту отдельно. Ограничьте число работников,
которые вызывают его методы. Создание клиентов, `Orders()` и `ReadNotices()`
не считаются внешними запросами.

Риск вычисляет ваш код. `SetRisk` проверяет существование заказа и указанных
строк, затем сохраняет результат внутри клиента. Исходный CSV он не меняет.
Вызов с неизвестной парой в `IsProblematic` возвращает ошибку проверки;
отсутствующий ответ нельзя считать `false`.

### Как связать этапы

Одна из возможных схем:

```text
Уведомления через ReadNotices
             |
      Поиск заказов
             |
      Проверка позиций
             |
            Tee
           /   \
          /     \
  Начальное      Сохранение
  событие        через SetRisk
          \     /
           Merge
             |
      Запись событий в stdout
```

Названия, число этапов и внутренние типы выбирайте сами. Для результата можно
использовать готовый `model.OrderCheck` или собственную структуру.

Развилка должна действительно работать: один результат идёт в ветку начального
события и в ветку сохранения. Пока один заказ сохраняется, другие могут
проверяться, публиковаться и сохраняться независимо от него.

**Событие `pending` нужно записать в stdout до начала `SetRisk` для этого заказа.**
Передать его в канал недостаточно: запись могла ещё не произойти. Например,
можно добавить к результату отдельный канал подтверждения публикации:

```go
type Delivery struct {
    Check     model.OrderCheck
    Published chan struct{}
}
```

Ветка сохранения ждёт `Published`. Этап отчёта закрывает этот канал после
попытки записать начальное событие. При ошибке вывода ожидания тоже нужно
освободить, чтобы программа смогла завершиться. Заказ с ошибкой проверки
ветка сохранения пропускает.

Каждый этап читает вход до закрытия, передаёт готовую работу дальше и перед
возвратом ждёт своих работников. Он не закрывает каналы, полученные от
`RunPipeline`. Пустой поток допустим на любом этапе.

## Формат отчёта

В stdout выводятся только события, по одному на строку:

```text
<state> <order_id> <true|false|unknown> <line_ids|->
```

Между полями ровно один пробел. Номера строк разделяются запятыми без пробелов,
идут по возрастанию и не повторяются. Для `false` и `unknown` вместо списка
ставится `-`. Каждое событие, включая последнее, заканчивается `\n`.

| Событие | Когда его выводить |
|---|---|
| `pending` | Риск известен, сохранение ещё не началось |
| `confirmed` | `SetRisk` успешно завершился |
| `error` после `pending` | Сохранение не удалось; риск и список строк остаются прежними |
| `error` с `unknown` | Проверка не удалась; других событий и сохранения этого заказа нет |

Например, второй заказ может сохраниться раньше первого:

```text
pending 1001 true 1,4
pending 1002 false -
confirmed 1002 false -
confirmed 1001 true 1,4
```

Примеры ошибок сохранения и проверки:

```text
pending 1003 true 2
error 1003 true 2
error 1004 unknown -
```

У каждого успешно проверенного заказа один `pending` и одно завершающее
событие. После завершающего события новые события этого заказа запрещены.
Порядок разных заказов произволен, но строки разных горутин не должны смешиваться.
При нормальном завершении незавершённых `pending` нет.

Диагностику пишите в stderr. После ошибки stdout допустим неполный журнал,
но программа должна освободить ожидающие горутины и дождаться всех запущенных
операций. Ошибка одного заказа не останавливает остальные.

## Входные данные

Все CSV содержат обязательный заголовок с фиксированным порядком колонок.
В таблице указаны пути относительно `testdata/`:

| Файл | Заголовок | Содержание |
|---|---|---|
| [products.csv](testdata/products.csv) | `id,sku,codes` | Каталог; дополнительные коды разделены `;`, пустой список допустим |
| [supplies.csv](testdata/supplies.csv) | `supply_id,supplier_id,product_id` | Состав поставок, одна строка на пару товар–поставка |
| [notices/*.csv](testdata/notices/) | `product_code,supply_id,reason` | Уведомления, которые читает `ReadNotices()` |
| [integration/orders.csv](testdata/integration/orders.csv) | `order_id,line_id,product_id,supply_id,quantity` | Позиции заказов для `orderclient.New()` |
| [integration/supplier-status.csv](testdata/integration/supplier-status.csv) | `product_id,supply_id,problematic` | Ответы для `supplier.New()`; флаг строго `true` или `false` |

В уведомлении кодом товара может быть SKU, штрихкод или код поставщика.
Проверять формат и контрольную цифру штрихкода не нужно. Причина `reason`
обязательна, но в расчёте риска не участвует.

Правила данных:

- Все ID и количества — положительные `uint64`. Записи `01` и `1` обозначают
  один числовой ID.
- ID товаров и их коды уникальны. Коды регистрозависимы; внешние пробелы удаляются,
  а внутренние пробельные символы, `:` и `;` в отдельном коде запрещены.
  Пустой элемент внутри непустого списка дополнительных кодов — ошибка.
- У поставки один поставщик и может быть несколько товаров. Пары товар–поставка
  не повторяются.
- Внутри заказа `line_id` уникален; в разных заказах может повторяться.
  Одна пара товар–поставка может встречаться в нескольких строках заказа.
- Ссылки на товары и пары поставок должны существовать. Неизвестный код или
  пара в уведомлении — ошибка входных данных.
- CSV только с заголовком допустим. Товар без заказов и уведомление, для которого
  не нашлось заказов, тоже допустимы.

Клиенты проверяют формат своих CSV, числовые поля и допустимость записей.
Ваш код проверяет связи между каталогом, составом поставок, готовыми заказами
из `Orders()` и уведомлениями из `ReadNotices()`. Таблицу статусов для этого
читать не нужно: её содержимое скрыто внутри клиента.

Есть два готовых набора:

| Набор | Каталог, поставки, уведомления | Данные клиентов | Заказы / позиции | Ожидаемые кандидаты |
|---|---|---|---:|---|
| Малый | [testdata/](testdata/) | [testdata/integration/](testdata/integration/) | 42 / 126 | 42 заказа |
| Большой | [testdata/large/](testdata/large/) | [testdata/integration/large/](testdata/integration/large/) | 20 000 / 46 000 | 6 000: из них 3 600 рискованных и 2 400 безопасных |

В малом наборе 9 товаров и 2 файла уведомлений с 10 строками. В большом —
5 000 товаров, 15 000 пар товар–поставка и 10 файлов уведомлений по 1 000 строк.
Есть повторы, разные коды одного товара, выбранные товары без заказов и заказы,
которые не должны попасть в отчёт. Строки больших CSV перемешаны.

`expected.txt` содержит конечные результаты в формате
`<risky> <order_id> <line_ids|->`, а не полный журнал событий.

## Запуск программы

CLI должен поддерживать четыре обязательных непустых флага:

```text
order-report -products <каталог.csv> -supplies <поставки.csv> -orders <заказы.csv> -supplier-status <статусы.csv>
```

Пути из `-orders` и `-supplier-status` передавайте конструкторам клиентов.
Поддержите формы `-name value` и `-name=value` в любом порядке.
Позиционных аргументов нет. Флаги `-h` и `-help` выводят справку в stdout
с кодом `0` и пустым stderr, без загрузки файлов.

### Два готовых файла с путями

В каждом наборе есть два отдельных входных файла. Они содержат только пути,
а сами CSV читают клиенты:

| Файл | Что внутри | Как использовать |
|---|---|---|
| [orders-input.txt](testdata/orders-input.txt) | Один путь к CSV заказов | Передать этот путь в `-orders`, затем в `orderclient.New()` |
| [suppliers-input.txt](testdata/suppliers-input.txt) | Пути к CSV уведомлений поставщиков, по одному на строку | Подать список в stdin; каждый путь передать в `supplierClient.ReadNotices()` |

Например, `testdata/orders-input.txt` содержит:

```text
testdata/integration/orders.csv
```

А `testdata/suppliers-input.txt` содержит:

```text
testdata/notices/supplier-007-part-01.csv
testdata/notices/supplier-008-part-01.csv
```

Для большого набора оба файла лежат в `testdata/large/` и ссылаются на его CSV.
Путь к таблице ответов поставщика задаётся отдельно флагом `-supplier-status`:
эта таблица нужна для `IsProblematic`, а уведомления определяют, что проверять.

Из stdin прочитайте список путей поставщиков, а каждый CSV загрузите через `ReadNotices(path)`.
Пустые строки пропускаются, внешние пробелы удаляются. Поддержите CRLF и
последнюю строку без `\n`. Пути разрешаются относительно рабочей директории
процесса. Путь с пробелами передаётся в списке без кавычек. Glob и запуск
shell для чтения списка не нужны. Пустой список даёт пустой отчёт без сохранений.

До первого события загрузите и проверьте входные данные. Ошибка даже в последнем
уведомлении отклоняет весь запуск с пустым stdout. После этой подготовки
готовые заказы должны продвигаться по конвейеру без ожидания проверки всей выборки.

| Код завершения | Значение |
|---|---|
| `0` | Успех, в том числе при рискованных заказах или пустом списке уведомлений |
| `1` | Ошибка stdin/stdout, проверки или сохранения заказа |
| `2` | Неверные аргументы, недоступный файл, плохой CSV или неверные ссылки в данных |

При успехе stderr пуст. При ошибке он содержит непустую диагностику;
точный текст не фиксируется. При коде `2` stdout пуст.

Пример запуска большого набора из `hw/02` после реализации:

```bash
go build -o /tmp/order-report ./cmd/order-report
read -r orders_path < testdata/large/orders-input.txt
/tmp/order-report \
  -products testdata/large/products.csv \
  -supplies testdata/large/supplies.csv \
  -orders "$orders_path" \
  -supplier-status testdata/integration/large/supplier-status.csv \
  < testdata/large/suppliers-input.txt > /tmp/order-report.txt
```

`read` берёт путь из `orders-input.txt` и передаёт его через `-orders`.
Перенаправление `<` подаёт `suppliers-input.txt` в stdin программы.
Перенаправление `>` сохраняет журнал событий из stdout в `/tmp/order-report.txt`.

Для малого набора используйте каталог, поставки и оба файла с путями из `testdata/`,
а статусы — из `testdata/integration/`.

## Ограничения

Подразумевают, что наличие подобного кода сразу отправляет вашу задачу на доработку

Пулы работников и очереди должны иметь ограниченный размер, не зависящий от
числа строк входа. Не запускайте отдельную горутину на каждую строку и не
делайте буферы размером со входной файл. Справочники, индексы и множества
для устранения повторов допустимы.

Не используйте `time.Sleep` для синхронизации и активное ожидание. У каждого
канала должен быть понятный владелец закрытия. Программа завершается только
после всех своих операций; после ошибок не должно оставаться зависших горутин.
Решение должно работать без гонок, в том числе при `GOMAXPROCS=1`.

## Критерии проверки

**Критерии ниже сформулированы в общих чертах и не могут рассматриваться как
чек-лист. Каждое решение будем рассматривать индивидуально
в контексте задачи, ибо оно достаточно творческое, чтобы не подгонять его под чеклист. Главное - чтобы решение проходило тесты и удовлетворяло
условию задачи. Обещаем рассматривать честно :)**

### Работа с каналами

- `RunPipeline` запускает произвольное число этапов одновременно, соединяет их
  ограниченными очередями и ждёт завершения всех этапов и их работников.
- Каждый этап вызывается через `stagetrace.Run`. Выходы закрываются после
  последней отправки, значения не теряются.
- `Merge` читает готовые входы независимо от медленных, сохраняет порядок
  каждого входа и передаёт все значения ровно один раз.
- `Tee` отправляет каждое значение в обе ветки в исходном порядке. Готовая
  ветка не ждёт освобождения другой для получения текущего значения, а следующий
  вход читается только после отправки текущего в обе ветки.
- Пустые, закрытые и `nil`-входы обрабатываются по описанным выше правилам.
  Заполненная очередь приостанавливает отправителя, а не растёт без ограничений.

### Заказы и работа с клиентами

- **CSV заказов, статусов и уведомлений читает готовый клиент.** В коде решения
  ему передаются пути, прямого чтения этих файлов и подмены ответов нет.
  Проще говоря, не нужно писать код для расчета проблематики и проставления рисков самим
- Разные коды одного товара сопоставляются правильно. Выбраны все нужные заказы,
  в том числе с безопасными поставками; лишних заказов в отчёте нет.
- Риск определяется по паре товар–поставка и ответу `IsProblematic`, а не только
  по товару. Найдены все рискованные строки, их номера отсортированы и не повторяются.
- Один заказ проверяется и сохраняется один раз. Повторы файлов, уведомлений
  и кодов не приводят к повторной обработке.
- Сохранение действительно выполняется через `SetRisk`, в том числе для `false`.
  При ошибке проверки риск остаётся неизвестным и сохранение не вызывается.
- Исходные CSV не меняются. Повторный запуск использует свои данные и актуальные
  ответы клиентов; результат не подогнан под готовый пример.

### Отчёт, аргументы и ошибки

- `pending` записан в stdout до начала `SetRisk` этого заказа, а `confirmed` —
  только после успешного ответа. Ошибки проверки и сохранения дают разные
  предусмотренные форматом события.
- У заказа нет повторных событий или переходов после завершения. Строки разных
  горутин не смешиваются, риск и номера позиций соответствуют результату проверки.
- Флаги, справка, список путей в stdin, формат stdout и коды завершения
  соответствуют разделу «Запуск программы».
- Некорректные входные данные отклоняются до первого события. Ошибка одного
  заказа не останавливает обработку остальных.

### Конкурентность и устройство решения

- Используются собственные `RunPipeline`, `Merge` и `Tee`, включая рабочую
  развилку отчёта и сохранения. Бизнес-логика вынесена из `main` в отдельные пакеты.
- Этапы передают результаты по мере готовности. Независимые заказы продолжают
  обрабатываться, пока другой заказ проверяется или сохраняется.
- Число работников и размеры очередей ограничены. У каждого клиента не больше
  8 одновременных запросов; нет горутины на каждую строку входа.
- Нет гонок, активного ожидания и `time.Sleep` для синхронизации. Решение
  работает и при `GOMAXPROCS=1`.
- Все запущенные операции завершаются. После ошибок, в том числе ошибки stdout,
  нет зависших отправителей и ожиданий. Готовые пакеты и фиксированные сигнатуры
  не изменены.
